# AUDIT 1: Auth + Session

**Linear:** PHO-238 (epic)
**Branch:** `investigate/audit-auth-2026-04-30`
**Auditor:** Claude (Opus 4.7)
**Date:** 2026-04-30
**Scope:** Auth & session handling — code-only investigation. No fixes.

## Summary

Audited the v1 auth surface across Clerk middleware, NextAuth fallback, custom XOR-token middleware, tRPC contexts (lambda/edge/async), Clerk webhook, payment webhooks (Polar/SePay), Casdoor/Logto webhooks, server actions, admin API routes, and Clerk metadata trust patterns. Found **34 issues**: **8 P0**, **6 P1**, **6 P2**, plus 14 observations & hardening opportunities.

The headline risks all converge on one pattern: **the codebase trusts unauthenticated identity claims more than it should**. Three interlocking weaknesses make a leak of any of {`KEY_VAULTS_SECRET`, `CLERK_SECRET_KEY`, `ADMIN_USER_ID`-typo} catastrophic:

1. **XOR-token + fallbackUserId** path lets a static-key payload override Clerk session expiration on `/webapi/chat/*`. (PHO-237 / `(backend)/middleware/auth/utils.ts:41-46`)
2. **Clerk `publicMetadata.planId`** is read as a paid-plan fallback in **9 server-side locations** — anyone with Clerk dashboard access can mint paid plans (vuthanhhuong-style abuse).
3. **Two server-action files in `(admin)/`** modify user points/plans/provider balances **without any admin auth check** at all.

Layer this on top of two `process.env.NODE_ENV === 'development'` backdoors that grant admin or `DEV_USER` impersonation, and a misconfigured `NODE_ENV` in any preview build is a full-takeover scenario.

Webhook signature verification is in good shape for the user-facing webhooks (Clerk, Polar, SePay credit-card), but **secret rotation status post-Vercel-April-2026 breach is unknown** and the signature comparisons in Casdoor/Logto/SePay use timing-vulnerable `===`.

## Critical findings (P0)

### A1.1 — Admin server actions have no admin auth check

- **File:** `src/app/[variants]/(admin)/admin/users/[id]/actions.ts:10-87`
- **File:** `src/app/[variants]/(admin)/admin/providers/actions.ts:10-41`
- **Issue:** Three server actions (`addPhoPoints`, `changeSubscriptionStatus`, `changeUserPlan`, `updateProviderBalance`) are exposed by Next.js as POST endpoints. They call `await auth()` only to capture an `adminId` for the audit log, but never validate that the caller is actually in `ADMIN_USER_IDS`. Any authenticated user who can discover the action ID (visible in the admin page bundle / network tab) can call them with arbitrary args.
- **Risk:** Any logged-in user can: top up arbitrary points to any user, change any user's `subscriptionStatus`, change any user's `currentPlanId`, or rewrite provider USD balances. The audit log records the attacker's own clerkId as `adminId`, giving false trust.
- **Estimated fix effort:** 30 min — add `await requireAdmin()` (already exists in `_shared/auth.ts`) at the top of each action and short-circuit on denial.

### A1.2 — Admin layout grants admin to _any_ signed-in user when `NODE_ENV === 'development'`

- **File:** `src/app/[variants]/(admin)/admin/layout.tsx:31-32`
- **Issue:** `const isAdmin = hasAdminRole || hasAdminEmail || isDev;` where `isDev = process.env.NODE_ENV === 'development'`. If a Vercel build, container image, or self-host deployment ever runs with `NODE_ENV=development`, every authenticated visitor becomes admin — this is the "hardcoded bypass token" Hien flagged in the 5-P0 list.
- **Risk:** Full admin UI access for any user. Vercel preview deployments can be configured to set `NODE_ENV` indirectly via build flags or Docker base images; a misconfigured `vercel.json`/`vercel.ts` would silently expose admin.
- **Estimated fix effort:** 5 min — drop the `isDev` clause entirely, replace with an explicit `ADMIN_USER_IDS` set check matching `_shared/auth.ts`.

### A1.3 — Dev-debug header impersonates `DEV_USER` / `MOCK_DEV_USER_ID`

- **File:** `src/app/(backend)/middleware/auth/index.ts:40-43`
- **File:** `src/libs/trpc/lambda/context.ts:79-82`
- **Issue:** Both the chat webapi auth wrapper and the lambda tRPC context check for header `lobe-auth-dev-backend-api: 1`. When set AND `NODE_ENV === 'development'`, they short-circuit auth to either `userId: 'DEV_USER'` (chat) or `userId: process.env.MOCK_DEV_USER_ID` (tRPC). Comment in lambda context claims "IT WON'T GO INTO PRODUCTION ANYMORE" — claim is unverified at runtime.
- **Risk:** Same as A1.2 — depends on `NODE_ENV` being incorrect in any deployment lane. There is no defense in depth; the static check is the only barrier.
- **Estimated fix effort:** 15 min — gate behind a positive allowlist (e.g. `process.env.PHO_ALLOW_DEV_AUTH_BYPASS === 'true'`) so a bare `NODE_ENV` slip is not enough.

### A1.4 — XOR token `fallbackUserId` accepted when Clerk session is missing

- **File:** `src/app/(backend)/middleware/auth/utils.ts:41-46`
- **File:** `packages/utils/src/server/xor.ts:31-44`
- **Issue:** `checkAuthMethod()` permits a request when `clerkAuth.userId` is missing **but** the XOR-encoded `Authorization` payload contains a `userId`. The XOR decoder is not authenticated — it's a Base64+XOR with the static `SECRET_XOR_KEY` (= `KEY_VAULTS_SECRET`). Anyone in possession of that single env var can mint a token impersonating arbitrary userIds. The justification in the comment ("multi-round tool calling chains where Clerk session cookies may expire between rounds") is real, but the fix should be a server-issued short-lived token, not a static-keyed XOR with a userId field.
- **Risk:** If `KEY_VAULTS_SECRET` ever leaks (leaked envs, log line, Vercel breach, .env.local check-in), full impersonation of any userId on `/webapi/chat/*` and any subsequent metering / subscription flow.
- **Estimated fix effort:** 4-8 hours — replace XOR userId-trust with either (a) a short-lived JWT signed by Clerk-issued JWKS, or (b) a HMAC-of-(userId|exp|nonce) with rotating server secret.

### A1.5 — `STAGING_TIER_BYPASS` returns all model tiers without calling `auth()`

- **File:** `src/app/api/subscription/models/allowed/route.ts:39-62`
- **Issue:** When the env flag is set AND `VERCEL_ENV` is `preview`/`development` OR `NODE_ENV` is `development`, the route returns `allowedTiers: [1, 2, 3]` _before_ calling `auth()`. An unauthenticated visitor on a preview deployment can hit this endpoint and get all-tier access metadata. Combined with the Clerk metadata fallback chain (A1.7), the client can flip into a paid tier without credentials.
- **Risk:** Low in production (env flag must be deliberately set), high in preview/QA where the flag is more likely flipped on. Also creates a code path where `planCode: 'staging_bypass'` flows downstream into metering/cost code that doesn't expect that string.
- **Estimated fix effort:** 30 min — move the bypass below the `auth()` check so at minimum it requires a signed-in user, and add a server-side allowlist of which userIds may use staging bypass.

### A1.6 — Clerk `publicMetadata.planId` is server-side source of truth for paid features

- **Files:**
  - `src/server/routers/lambda/user.ts:155-165` (getUserState)
  - `src/services/subscription/modelAccess.ts:134-138`
  - `src/app/api/artifact-ai/route.ts:35-39`
  - `src/app/(backend)/webapi/chat/[provider]/route.ts:431-435`
  - `src/app/api/subscription/usage-stats/route.ts:115-119`
  - `src/app/api/subscription/models/allowed/route.ts:121-125`
  - `src/app/api/research/ai-summary/route.ts:36-40`
  - `src/app/api/promo/activate/route.ts:121-130` (the writer)
  - `src/features/MedicalBeta/FeedbackButton.tsx:215` (read on client; OK alone but reinforces the pattern)
- **Issue:** When the DB resolves to a free plan, the server falls back to `clerkUser.publicMetadata.planId` and treats it as authoritative for entitlement decisions. Anyone with Clerk dashboard write access (admins, support agents, anyone with a leaked `CLERK_SECRET_KEY`) can mint any plan for any user without leaving a row in the `subscriptions` table. This is the **vuthanhhuong** pattern: paid features attached to Clerk metadata that bypasses the payments DB.
- **Risk:** No DB audit trail for plan grants. A compromised support account, a leaked `CLERK_SECRET_KEY`, or a buggy promo flow that writes Clerk-first / DB-never (see A1.8) all lead to silent, unbacked paid features.
- **Estimated fix effort:** 1-2 days — make the `subscriptions` table the single source of truth; if a Clerk metadata fallback is needed for cache freshness, gate it behind a `subscriptions.paymentProvider IS NOT NULL` check or remove entirely. Also: write an admin job to backfill DB rows from Clerk metadata for any current free-DB-but-paid-Clerk users so the fallback can be deleted safely.

### A1.7 — Clerk metadata-first promo activation can drift past DB

- **File:** `src/app/api/promo/activate/route.ts:118-206`
- **Issue:** Step 1 writes Clerk `publicMetadata`, Step 2 writes the DB. If Step 2 throws (line 203 catches and logs, but does not roll back Clerk), the user has Clerk-paid-plan but no DB record. Combined with A1.6, the user retains paid features indefinitely — Clerk fallback paths never see a discrepancy.
- **Risk:** Medium-to-high. Net result is a free user looking paid in production; promo abuse is silent. Also: the in-memory `codeUsageCount` (line 49) is not actually decremented if either step fails _after_ line 227's increment runs — but the increment runs only on the success path, so this is mostly OK.
- **Estimated fix effort:** 4 hours — invert the order (DB first, Clerk second), or wrap both in a saga / retry-with-rollback. Consider dropping Clerk metadata sync entirely and relying on read-time joins (per A1.6).

### A1.8 — `MANUAL_PAYMENT_VERIFY_ENABLED` lets a user self-activate their own pending payment

- **File:** `src/app/api/payment/sepay/verify-manual/route.ts:32-198`
- **Issue:** When the env flag is on (defaults off, but accept either `MANUAL_PAYMENT_VERIFY_ENABLED=true` _or_ `NEXT_PUBLIC_ENABLE_MANUAL_PAYMENT_VERIFY=true`, line 13-14), any authenticated user can POST `{ orderId }` and the route will mark **their own** pending `sepayPayments` row as `success` and call `activateUserSubscription()`. The only check is `payment.userId === userId` — but the user created that payment row when they clicked "Pay", so the check trivially passes.
- **Risk:** If the flag is ever flipped on in production for any reason (debug, support workaround, copy-paste from staging), every signed-in user gets free paid subscription on demand. The fact that the second flag is `NEXT_PUBLIC_*` (client-readable) makes the feature state discoverable.
- **Estimated fix effort:** 1 hour — require a signed admin token, or restrict to `requireAdmin()`. Remove the `NEXT_PUBLIC_*` variant entirely (it leaks state and serves no purpose since the route is server-only).

## High priority (P1)

### A1.9 — Promo code usage count is in-memory only

- **File:** `src/app/api/promo/activate/route.ts:49, 227`
- **Issue:** `codeUsageCount` is a module-scoped object. On Vercel Functions, every cold start (and every isolate) gets its own copy. The `maxUses: 200` limit on `PHO-MED-2026-BETA` is therefore not enforced — a single user could run the activation 200+ times across cold starts, or Vercel could scale to N isolates each running 200.
- **Risk:** Medium. The promo code itself isn't unlimited revenue, but a determined attacker can inflate `medical_beta` activations beyond the planned cap.
- **Estimated fix effort:** 2 hours — track in `subscriptions` or a new `promo_redemptions` table with a unique index on `(promoCode, userId)`.

### A1.10 — `/api/subscription/activate-free` re-mints points on every call

- **File:** `src/app/api/subscription/activate-free/route.ts:51-61`
- **Issue:** The handler `UPDATE`s `phoPointsBalance: 50_000` unconditionally. A free user who has burned through their balance can POST to this endpoint to reset back to 50k. There is no idempotency check or "only on first activation" guard.
- **Risk:** Quota bypass for free users. Combined with the chat metering decreasing the balance, this is a free-token loop.
- **Estimated fix effort:** 30 min — only set `phoPointsBalance` when no active subscription row exists, or use `pointsResetDate` to gate.

### A1.11 — `checkAuth` swallows subscription DB errors and admits the request

- **File:** `src/app/(backend)/middleware/auth/index.ts:162-166`
- **Issue:** `try { … checkTrialAccess … } catch (error) { console.error(…); /* don't block */ }`. A database outage, a query bug, or a runtime error in `SubscriptionService` allows the request to proceed with no entitlement check.
- **Risk:** During DB incidents, all chat requests bypass the subscription gate. Recoverable, but exactly the kind of behavior that explains under-billing during the Clerk crisis window.
- **Estimated fix effort:** 1 hour — fail closed (return 503 `SubscriptionCheckUnavailable`), or at least log to Sentry with a high severity and add a circuit-breaker to surface the outage.

### A1.12 — Webhook signatures use non-constant-time `===` comparisons

- **File:** `src/app/(backend)/api/webhooks/casdoor/validateRequest.ts:24` (`casdoorSecret === secret`)
- **File:** `src/app/(backend)/api/webhooks/logto/validateRequest.ts:36` (`signature === logtoHeaderSignature`)
- **File:** `src/app/api/payment/sepay/webhook/route.ts:509` (`providedSecret !== webhookSecret`)
- **Issue:** All three compare secrets/signatures with JavaScript `===`. While timing attacks are mostly theoretical for short HMAC outputs over WAN, constant-time compare (`crypto.timingSafeEqual`) is the standard, and the V8 string compare can short-circuit on length mismatch.
- **Risk:** Low-but-real, especially for SePay's static webhook secret which is the only barrier on bank-transfer callbacks (signatures aren't sent for VietQR).
- **Estimated fix effort:** 30 min total — replace each comparison with `crypto.timingSafeEqual` after length normalization.

### A1.13 — `asyncTrpc` trusts (KEY_VAULTS_SECRET, userId) tuple as auth

- **File:** `src/libs/trpc/async/asyncAuth.ts:18-22`
- **Issue:** Background async tRPC procedures authenticate by checking `ctx.secret === serverDBEnv.KEY_VAULTS_SECRET` and a free-form `ctx.userId`. The same secret is used for the XOR token (A1.4), so it has dual-use exposure. A leak gives both impersonation on the chat API and the ability to enqueue arbitrary background jobs as any user.
- **Risk:** Same compounding risk as A1.4. The async path is not user-facing, but `image`, `file`, and `ragEval` async routers can spend money on the wrong account.
- **Estimated fix effort:** 4 hours — separate the async-job HMAC from `KEY_VAULTS_SECRET`, and rotate.

### A1.14 — Polar SDKValidationError fallback parses unsigned-by-SDK events

- **File:** `src/app/api/payment/polar/webhook/route.ts:140-159`
- **Issue:** `validateEvent()` is wrapped to catch `SDKValidationError`, after which the code does `event = JSON.parse(body)`. The signature _was_ verified before SDK schema validation failed, so this isn't an auth bypass — but the comment is right that the handler then trusts a payload Polar's SDK considered malformed. The handlers downstream (`event.type === 'checkout.completed'`, `event.data.product_id`, etc.) assume a known shape.
- **Risk:** Low for now. As Polar evolves event types, this fallback could process events the team hasn't reviewed; combined with currency assumptions (`event.data.amount / 100`) it could write incorrect billing rows.
- **Estimated fix effort:** 1 hour — log the fallback to Sentry and add an explicit allowlist of `event.type` values that are safe to parse without SDK schema.

## Medium priority (P2)

### A1.15 — Hardcoded promo codes in source bundle

- **File:** `src/app/api/promo/activate/route.ts:34-46`
- **Issue:** `PHO-MED-2026-BETA` and `PHO-MED-2026-VIP1` are committed in source. The comment on line 26 says "in production, move to DB or env var" — the TODO is unmet. Anyone with repo read access (or ability to inspect the server bundle) sees them.
- **Risk:** Low — these are intentionally distributable codes. Still: rotation requires a code deploy.

### A1.16 — Referral code is reversible base64 of clerkUserId

- **File:** `src/app/api/invite/route.ts:19`
- **File:** `src/app/api/referral/track/route.ts:35`
- **Issue:** `Buffer.from(userId).toString('base64url').slice(0, 12)` is reversible (and worse: truncated, so prefix-collision is possible in theory). Track route blindly base64-decodes back to a clerkId.
- **Risk:** Low — referral fraud (fake referrals to nonexistent users); not an auth issue. Truncation collision risk is essentially 0 for current user-base size but should be measured.

### A1.17 — Three different admin authorization strategies

- **Layout:** `(admin)/admin/layout.tsx` — `role || email || isDev`.
- **API helper:** `api/admin/_shared/auth.ts` — only `ADMIN_USER_ID` env.
- **Bulk actions:** `api/admin/bulk-actions/route.ts` — both `requireAdmin()` AND a separate Clerk role check (with silent try/catch fallback at line 54-58).
- **Issue:** Inconsistent admin definitions mean an admin who logs in via the UI may be unable to use the API (or vice versa). The silent try/catch in bulk-actions makes the role check non-load-bearing.
- **Risk:** Functional confusion + defense-in-depth that doesn't actually layer. Not a direct exploit.

### A1.18 — `NEXT_PUBLIC_ENABLE_MANUAL_PAYMENT_VERIFY` leaks server feature state to client

- **File:** `src/app/api/payment/sepay/verify-manual/route.ts:14`
- **Issue:** A `NEXT_PUBLIC_*` env var inlined into the client bundle telegraphs whether the manual-verify endpoint is on. Unrelated to A1.8 functionally but together they add discoverability.
- **Risk:** Low.

### A1.19 — `DESKTOP_USER_ID` is a single shared identity across all desktop installs

- **File:** `src/libs/trpc/edge/index.ts:28` and `lambda/index.ts:29`
- **Issue:** Every desktop user is treated as the same userId. This is a desktop-only concern (the cloud is unaffected) but the same code path runs on web if the `isDesktop` constant ever flips.
- **Risk:** Desktop-specific; not relevant to v1 cloud unless the build flags drift.

### A1.20 — Clerk webhook env-validation only fires under `isServerMode`

- **File:** `src/app/(backend)/api/webhooks/clerk/route.ts:11-13`
- **Issue:** The `throw new Error('CLERK_WEBHOOK_SECRET is missing')` is conditional on `authEnv.NEXT_PUBLIC_ENABLE_CLERK_AUTH && isServerMode`. The route itself uses `authEnv.CLERK_WEBHOOK_SECRET!` (non-null assertion). If Clerk is enabled but the validation guard's env flags read differently than the route's runtime env (e.g. stale build, edge runtime), the route invokes `new Webhook(undefined)` and svix's behavior on `undefined` secret is the failure mode.
- **Risk:** Low — would only manifest under env-misconfiguration, but the assertion lies.

## Observations / Hypotheses

These are not yet confirmed bugs but are worth a closer look in a follow-up audit.

- **O1.** `isDesktop` constant is loaded from `@/const/version` — a single mis-configured build env (`NEXT_PUBLIC_DESKTOP=1`?) would silently grant all users `DESKTOP_USER_ID`. Check whether Vercel build args ever set this.
- **O2.** `clerkAuth.getAuthFromRequest()` falls back from `authenticateRequest()` to `auth()` on error (clerk-auth/index.ts:30-43) — this can silently mask Clerk outages, returning `null` userId when `auth()` would otherwise have surfaced an error. Combined with A1.4, a Clerk outage + a known XOR secret = full bypass.
- **O3.** `CLERK_DEV_IMPERSONATE_USER` env mapping at `clerk-auth/index.ts:88-98` allows mapping `dev` → `prod` userIds **only when `NODE_ENV === 'development'`**. Same NODE_ENV-trust concern as A1.2 / A1.3.
- **O4.** OIDC path in `lambda/context.ts:108-143` returns early on success but does not invalidate the OIDC JWT against a session store — if a Clerk session was revoked but the OIDC token is still in TTL, the stale token wins. Verify behavior with a test that revokes a Clerk session and replays an OIDC token.
- **O5.** `subscription/models/allowed/route.ts` sets `Cache-Control: private, max-age=300` (line 161). For an unauthenticated request returning `vn_free` defaults, `private` is fine, but Vercel's default routing sometimes treats query-less GETs as cacheable upstream; verify the CDN config does not drop the `private` directive.
- **O6.** `defaultMiddleware` (middleware.ts:79-81) blocks `/.env*` probing — good. But it does not block `/api/.env`, `/admin/.env` after the rewrite is applied; the regex covers both — verify with a request to `/admin/.env.local`.
- **O7.** `clockSkewInMs: 60 * 60 * 1000` (middleware.ts:333) — a 1-hour clock skew tolerance for Clerk. This is the maximum the codebase has seen suggested; usual default is 5 min. If Clerk releases a guidance update post-jwk-kid-mismatch, lower this.
- **O8.** `Clerk metadata sync after payment` (sepay webhook lines 280-302, polar lines 301-323) — both do `fetch(`<https://api.clerk.com/v1/users/${userId}/metadata`>, ...)`directly with`CLERK_SECRET_KEY\`. No retry, no DLQ. If Clerk is down at the moment the webhook lands, the user is in DB-paid / Clerk-free state — same drift as A1.7 but the other direction.
- **O9.** No webhook idempotency on Clerk webhook (`(backend)/api/webhooks/clerk/route.ts`) — if Clerk re-delivers a `user.created`, it will hit `userService.createUser` and `phoWallet.insert(...).onConflictDoNothing()` — `onConflictDoNothing` saves the wallet but the user-service code path is not visible from the audit; should verify.
- **O10.** Polar webhook trusts `customer_email` from event payload to look up the user (line 169-194). If a customer changes email between checkout and webhook delivery, the lookup fails and the subscription never activates — and the webhook returns 404 to Polar, who will retry, but the customer paid. This is a UX bug but also a billing-correctness concern.
- **O11.** `payment-method/route.ts` and `current/route.ts` are listed as Clerk-using but not audited line-by-line; verify they don't repeat the publicMetadata trust pattern.
- **O12.** Manual payment verify route (A1.8) calls `activateUserSubscription` which is not visible in this scan; verify it doesn't grant points/credits beyond plan defaults.
- **O13.** The audit log writers in admin actions all run AFTER the modification (lines 25, 49, 73, 91, 105 in users/\[id]/actions.ts). If the audit insert fails, the modification is already committed. Use a transaction or write-ahead audit.
- **O14.** `defaultMiddleware`'s `MIDDLEWARE_REWRITE_THROUGH_LOCAL` rewrite (line 137-148) sets `url.protocol = 'http'` and `url.host = '127.0.0.1'` — verify this never triggers in production via leaking env (`PORT` is set on Vercel by default to a non-3210 value, which would expose the wrong port).

## Recommended fix order

This order minimizes user-visible churn while closing the highest-blast-radius gaps first.

1. **A1.1** (Admin server actions, no auth) — 30 min, no UX impact, prevents arbitrary user privilege escalation. Ship in next deploy.
2. **A1.2** (admin layout `isDev` bypass) — 5 min, same deploy as A1.1.
3. **A1.10** (`/activate-free` re-mints points) — 30 min, plug a free-token leak before users notice.
4. **A1.8** (Manual sepay verify) — 1 hour. Even if the flag is currently off, harden it before someone re-enables for "support reasons".
5. **A1.5** (STAGING_TIER_BYPASS without auth) — 30 min. Move the auth check above the bypass.
6. **A1.3** (Dev-debug header) — 15 min. Convert from `NODE_ENV` check to explicit positive flag.
7. **A1.11** (Subscription DB error → admit) — 1 hour. Fail closed.
8. **A1.12** (Constant-time compares) — 30 min. Combine with secret rotation.
9. **A1.7** (Promo Clerk-first → DB) — 4 hours. Invert order; add saga.
10. **A1.6** (Clerk publicMetadata.planId trust) — 1-2 days. Largest blast radius but biggest scope. Plan it as Phase 1 of a "DB is source of truth" cleanup.
11. **A1.4** + **A1.13** (XOR/KEY_VAULTS_SECRET unification) — 4-8 hours. Rotate secret, split the two usages, replace XOR with HMAC-bearing token.
12. **A1.9** (Promo in-memory limit) — 2 hours. Move to DB.
13. **P2 cleanup** — A1.15 → A1.20 in any order; bundle with the next refactor PR.

**Pre-fix safety check:** before rotating `KEY_VAULTS_SECRET`, audit how it's referenced — it gates user keyVault decryption (`KeyVaultsGateKeeper`) and async tRPC; rotation needs a re-encrypt migration. This is itself a P0-level change-management risk.
